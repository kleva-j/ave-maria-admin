# Twenty staging server

This directory runs an isolated, single-workspace Twenty staging instance. It
uses the official Twenty server image with PostgreSQL, Redis, and local file
storage. The web port is bound to localhost; use a tunnel profile only when
remote access is needed.

## Start the instance

Requirements: Docker with Compose v2 and OpenSSL.

```sh
./scripts/setup.sh
docker compose up -d
docker compose ps
```

Open [http://localhost:3000](http://localhost:3000) to complete the initial
workspace setup. Do not put production customer data in this staging workspace.

The setup script creates `.env` and fills any missing generated values with
random database, encryption, and application secrets. Existing non-empty values
are preserved. It also builds `PG_DATABASE_URL` from the database values for
Compose. That file is ignored by Git. Back up the database volume and encryption
keys together; the encrypted data cannot be recovered without them.

## Temporary public URL

Tunnel domains are generated by the provider and can change after a restart.
Twenty needs `SERVER_URL` to match the public HTTPS URL for correct links and
authentication callbacks. Start the server locally first, then start one tunnel.

### Cloudflare Quick Tunnel

```sh
docker compose --profile cloudflare up -d cloudflare-tunnel
docker compose logs -f cloudflare-tunnel
```

Copy the generated `https://….trycloudflare.com` address into `SERVER_URL` in
`.env`, then recreate Twenty so it loads that URL:

```sh
docker compose up -d --force-recreate server worker
```

### ngrok

Add your ngrok authtoken to `NGROK_AUTHTOKEN` in `.env`, then run:

```sh
docker compose --profile ngrok up -d ngrok-tunnel
docker compose logs -f ngrok-tunnel
```

Copy the generated HTTPS URL into `SERVER_URL` and recreate the server and
worker as shown above. If a tunnel URL changes, update `SERVER_URL` and repeat.

Use only one tunnel profile at a time. Random tunnel URLs are convenient for
staging, but are not stable production endpoints. Anyone who obtains the URL
can reach the sign-in page; Twenty authentication still controls workspace
access. PostgreSQL and Redis are not exposed through the host ports.

## Develop and apply the CRM schema app

The companion app lives in `../twenty-crm` and uses Twenty's Yarn 4 toolchain.
Use Node.js 24.5 or newer (the repo's app-area Node selection may be older),
then install and build its dependencies:

```sh
cd ../twenty-crm
corepack enable
yarn install
```

After the server is reachable at its current `SERVER_URL`, install the official
Twenty CLI and authenticate to the staging workspace:

```sh
npm install --global twenty@2.51.3
twenty auth login --url http://localhost:3000
twenty app build
twenty app plan
twenty app apply --create
```

If authenticating through a tunnel, replace the local URL with the current
HTTPS URL printed by ngrok or Cloudflare.

Review the plan before applying changes. The app defines customer fields on
Twenty's standard Person object and custom records for withdrawals, KYC
metadata, risk holds, savings plans, transactions, and masked bank-account
summaries. Each operational record has a native Person relation and carries the
stable AVM user ID for matching. Phase 1 does not yet synchronize live app data.

The CLI stores authentication outside this repository in the user's Twenty
configuration directory. Never commit API keys, `.env`, or tunnel credentials.
